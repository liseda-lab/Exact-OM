# XR-2.1 implementation migration and acceptance

**Reviewed revision:** `b4c1ed0d5e12c45974bdcb4d230fb2ab6c6deb04`, 29 September 2026. **Specification date:** 30 September 2026. This is a work list, not a record of completed fixes. Line references below describe that reviewed revision and may move during implementation; function/module identity is authoritative.

**Post-implementation follow-up:** an XR-2.1 implementation now exists at `6f6a3e0038dbd5898126a34b28dee1faa06ef2f3`. [14 Implementation review](14-implementation-review.md) records the remaining defects and gaps against that implementation, with required fixes, regression tests and compatibility rules. The findings below remain the historical migration baseline; do not assume every item is still absent or already closed.

## Preserve what already works

The implementation already contains complete replacement bundles, a shared-core OWL representation, HGT/R-GCN model controls, a conditioned SDD generator, unary and pairwise value heads, exact PySAT selection and hash-bound verification reports. Unknown plans remain pending rather than becoming false logical exclusions. Retain these foundations. No false-optimality defect was established for the current frozen-pool contract by the review; the revision extends coverage, cuts, training and operational reliability without discarding that contract.

Current symbolic teacher/value code already supports verified partial caches for some whole-repair losses. The new sampled training work must reuse this rather than claim that all existing learning is exhaustive. The missing capability is systematic supervision on newly generated candidates, informative interactions and approximate proposal targets.

Keep archived pilot data/checkpoints immutable. Do not retroactively change status, target values, split labels or circuit language and then compare the rewritten rows with the original report. New feature/record versions need explicit adapters and tests as specified in [01](01-architecture-and-contracts.md).

## Integration sequence and code ownership

1. **Records and correctness:** `records.py`, `api.py`, `workers.py`, `exact/repair/study.py`, `tools/repair/corpus.py`. Add strict migration, policy validation, fair baseline accounting and omission fixtures first.
2. **Generation:** `candidates.py`, `grammar.py`, `circuit.py`, `compilation.py`, `proposals.py`, `pipeline.py`. Preserve public action semantics and optional imports; replace internals only as required by CG contracts. Use a narrow cache helper, not a new framework.
3. **Reasoning and selection:** `owl.py`, `kernel.py`, `maxsat.py`, `evaluation.py` and the existing backend integration points. Prefer a small detector adapter over reimplementing a full reasoner. If external extension code is unavailable, the report alone is not executable evidence: implement and qualify only the explicit supported subset before calling it sound.
4. **Learning:** `graph.py`, `model.py`, `learning.py`, `tools/repair/train.py` and data/collection tooling. Centralise shared transformations; store training-only answers separately. Add the plan-risk readout to the shared encoder before considering a second graph backbone.
5. **Evaluation:** `exact/repair/study.py`, reporting/export and strict protocol loader. Preserve old result readers; create separately identified new runs. Add LLM annotation as an offline, bounded data-production step using the existing `LLMRouter`, `OpenRouterClient` and `RequestLedger` in `exact/llm/`; it is not an inference-time dependency or a new provider integration. The existing client already supplies hosted calls and durable request accounting; new work supplies the repair evidence and label contract.

Prefer existing modules and dataclasses. Split a module only when its current responsibility becomes unclear. No generic RL environment, new OWL parser, new MaxSAT implementation or replacement circuit library is required for XR-2.1.

## Conformance suite to implement

Use real adapter tests as well as the existing finite truth model. Required layers are:

- **Materialisation/policy:** all action bundles; public/private vocabulary; imports and duplicate occurrences; no stale closure; all-off infeasible; source/union distinctions; direct-record/API equivalence.
- **Circuit:** brute-force support, normaliser, marginal, sample and gradient checks on tiny grammars; unused/fixed bits; nonunique encodings; family decomposition; immutable versus editable semantic support; cache corruption; zero valid mass; per-family resource failure without lost elementary alternatives.
- **Graph/model:** hand-constructed graph/edge/feature fixtures; identical pair selectors; attention masks; proposal versus completed-candidate/risk input separation; batch versus single inference; cost not counted in benefit; permutation and pair anchoring checks.
- **Labels/training:** exhaustive finite teacher against direct enumeration; partial masks; no unsupported/timeout negatives; three-way conflicts; quartet contrasts; sampled candidate identities and split inheritance; held-out leakage traps; missing teacher mass; checkpoint-order regression.
- **Solver/verification:** exhaustive small-instance equality with unary/pair objectives and signed factors; monotone versus nonmonotone cuts; duplicate origins and active-expression clauses; all shortlisted/deferred unknowns in bounds; first feasible master optimum closes gap; new epochs invalidate old objective bounds.
- **Operations:** forced failure during serialisation, compilation, solve, support extraction and classification; bounded retries/cleanup; completed negative events survive; no partial positive acceptance; concurrent cache publication and stale-import invalidation.
- **Semantic fidelity:** known synthetic contrasts distinguish meaningful context from arbitrary coherent narrowing; cost-only changes do not alter meaning labels; order swaps/ties/abstentions; held-out judge separation; identical/redundant plan controls; explicit score calibration.

Each test artefact records the exact input, expected invariant, observed status and backend scope. Finite tests never replace OWL conformance. Performance thresholds are development benchmarks with measured variance, not brittle unit-test timing assertions.

## Release and experiment gate

Before an XR-2.1 experiment, provide: requirement-to-test coverage; updated schema/feature manifests; qualified backend support matrix; tiny exhaustive circuit/solver agreement; generated-pool development report including failures; frozen collection/label/evaluation protocols; and the strict new run manifest. [08](08-experiment-matrix-and-handoff.md) specifies the dependency gates.

Do not resume old training with newly changed labels/features under the same checkpoint ID. An explicit warm-start arm may load compatible weights while resetting new heads/optimiser state and recording what was transferred. It is not a continuation of the archived run.

Before product enablement, separately review acceptance scope, patch export and deployment resource policy. This specification task does not implement these changes, launch experiments or enable repair by default.
