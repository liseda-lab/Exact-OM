# Primary evaluation execution preparation

`python -m tools.repair.prepare_primary_evaluation prepare CAMPAIGN OUTPUT` reads only the authenticated schedule declarations, committed engineering reports and current resource ledger. It creates disabled execution manifests covering all 1,535 repair/pool rows, 518 comparison references and 18 case-complete shards. The metadata audit recomputes the mapping without opening any TEST observable, evaluator, ontology or matcher payload. The original schedule and reports remain immutable.

`tools.repair.primary_evaluation` connects the rows to native deletion, observable-score greedy deletion, local asserted-query support, budgeted complete-plan query search, generated learned repair, fixed-pool learned scoring and the matched circuit/grammar proposal paths. An absent observable score/query basis is unavailable; hidden evaluator queries never substitute for it. Direct deletion constructs no rich pool; deletion after rich generation retains its separate charged row. E2 consumers share one bound pool. E4 changes only risk ordering, and E5 only the staged/one-stage schedule. E6 refers to existing E1/E2 outputs. Shared costs are charged once by run identity, rather than again for each comparison.

Every executing shard has one file-lock owner, immutable row receipts and content-bound output artifacts. A started row without a completion requires ownership/ledger reconciliation; its reservation remains charged and its case deadline is never renewed. Logical unknown, unsupported and resource-limited outcomes are terminal scientific rows. A software failure persists its receipt, stops that shard and retains all remaining rows as not attempted. The runtime requires the exact selected-model freeze receipt, Slurm-visible GPU UUID and a charged evaluation/GPU stage owner. It clips work to the case, worker and existing stage deadline, reserving the final eight evaluation hours. Nested workers inherit the enclosing call deadline and cleanup allowance. No hosted client is used during inference.

The 128 semantic comparisons and 26 independent order swaps remain a separate disabled annotation schedule. Conference keeps 43 slots: 42 paired supervision contrasts and one explicitly separate combined-versus-observable control. All 21 pair declarations and seven inherited TEST pairs remain visible. The implementation does not materialize Conference TEST payloads during preparation; post-freeze source-bound materialization, native capability status, exact selected outputs and independent assessment remain admission dependencies.

The endpoint projection retains all 128 TRAIN declarations, 126 caches, 99 measured updates and 27 unmeasured cached cases. It assigns the slowest observed update to unmeasured cases and includes the process/update timing gap in every epoch, since optimizer checkpointing occurs outside the update timer. That gap is not a measured pure setup cost. The additional boundary reserve and 70% residual model/stage capacity form an explicitly conservative scenario, not an upper-bound guarantee or a complete paired throughput qualification.

The successor DEV template explores 30 seconds of repair plus the unchanged 182-second semantic reserve and another 90 seconds for independently audited slots. It retains 384 rows, 64 semantic slots and 14 swaps with equal paired budgets; each protocol's final reserve is the exact remaining final schedule. The current conservative projection admits no endpoint beyond the first epoch-5 DEV pass. The old epoch-50 template is therefore still disabled. Qualified teacher service, grounded shared weak labels, TRAIN-only scale, paired combined-loss throughput and a valid common endpoint must be resolved before fitting. No request, stage-time or monetary amendment is made by this preparation.

The disabled shard descriptors conservatively reserve the inference GPU for the entire row, including native checking and idle time. Their 114,240-second reservation, including shard setup/cleanup, exceeds 70% of a single GPU's 40-hour repair-launch window (100,800 seconds). The earlier schedule assumed two repair workers; that assumption is not silently treated as two GPU owners. `execution-capacity.json` therefore blocks admission pending qualified CPU controls/shared-pool ownership or a serialized inference service. All original rows and limits remain intact; preparation does not assert that these descriptors are ready to execute TEST.
